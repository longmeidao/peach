# ADR-0038：分歧按字段优先级链自动结算，复核只留身份类问题

- 状态：Accepted
- 日期：2026-09-22

## 背景

ADR-0018 起，自动落库的判据一直是「没有分歧」：一个字段上但凡有第二种取值，整行就交人工。
ADR-0025、0034、0035 每次都只在这条线上凿一个洞——多来源一致、只剩 javdb、只剩官方——洞与洞
之间留下的是同一类行：两家都给了值、两家都不算错、谁也不比谁更值得问用户。

2026-09-22 用户给出的判断是「Peach 也要尽量追求无复核，没人喜欢复核，只有真的错的、无法判断
的才需要复核」。

对真实账本当前队列（7250 行候选、438 行活着）做了一次只读普查，这 438 行的构成是：

- **62 行官方来源之间有分歧**，逐条看下来 100% 是同一种：mgstage 与 dmm/libredmm。mgstage 是
  转售店，它的标题缀着店铺加赠（`ラグジュTV 1492 ~店舗特典付き~`）、系列写的是店内货架名。
  这不是「哪家写错了」，是店铺口径与片商口径的差别，而片商口径才是这部片的事实。这 62 行
  在页面上根本看不到——`_drop_shop_side_dissent` 早就把它们藏起来了——但谁也没结算它们，于是
  它们无限期地停在「未决」。其中 60 行同时满足其余各道门槛（番号、文件名、字段归属）。
- **111 行是非官方来源挑战账本已有的值**，其中 107 行来源只有 javbus 一家。ADR-0035 记下的
  失败模式就是它：搜不到就给首个近似命中。
- **69 行出演者栏写的是企划名义**（`めぐみ 28歳 パパ活女子`、`飛鳥ちゃん`）。ADR-0025 判定
  不从宣传语里猜人名，于是它们一直等着人工。抽查发现本机快照里常常直接写着正式艺名：
  `200GANA-2245` 的 Seesaa 素人系総合 Wiki 那一行写的是 `目黒めぐみ`。
- **78 行标签候选里混着一个三张表都不认的词**。整行十几个认得出的标签陪着那一个生词一起
  等人，而等来的判断只关乎那个词。
- 余下是身份类：文件名认不出番号 46、韩国 MIB 番号问了 JAV 目录站 42、候选自报番号对不上
  19、账本已无该番号资产 8。

参考产品 amane 的做法与这个形状对得上：`content_routes` 定站点顺序，`field_priority` 是稀疏
例外，`field_blacklist` 压在一切之上，标量字段沿链短路取第一个有效值。

## 决策

**一、每个字段按一条来源优先级链取值，链上排第一的那家胜出。**

链的层级，由高到低：

1. `local_nfo`——本机已有的 NFO，它是前一次复核或用户自己写下的结果；
2. 官方来源（`SOURCE_SPECS[...].official`，含 official_mirror）；
3. `PREFERRED_COMMUNITY_SOURCE`（javdb）；
4. 其余 community 来源；
5. `FALLBACK_SOURCES`（javbus）。

同层之间按既有的 `FIELD_SOURCE_ORDER` 排序。`release_date` 的同层并列照 ADR-0034 决策三先按
番号日期定；其余字段取链上第一个非空值。被压下的取值连同它的来源写进 `review_decision.note`
的 `overruled`，规则名记 `adr-0038-chain-<胜出来源>`。

**同一家给出两个不同取值时不结算。** 那不是来源之间的排序问题，链答不了。

**二、允许按字段指定优先来源与黑名单**，即 amane 的 `field_priority` 与 `field_blacklist`：
`metadata_policy.FIELD_SOURCE_PRIORITY` 把某家提到该字段链首，`FIELD_SOURCE_BLACKLIST` 让某家
在该字段上不说话，黑名单压在优先级之上。两张表都是稀疏例外，与既有元数据策略同处一层，随
`resolve_policy(profile=...)` 生效。本机当前一条例外都不需要，两张表都是空的。

**三、兜底来源挑战账本已有的值，整行不进队列。** 现值非空、而候选来源全在 `FALLBACK_SOURCES`
里时，这一行没有可判的东西：ADR-0035 已经判过它的取值不当证据，留着只是要人再认一遍
「这个不能点」。

**四、能改掉账本已有值的仍然只有 `local_nfo` 与官方来源。** ADR-0033 的「community 只补空」
边界不变；链解决的是取哪个值，不是能不能覆盖。

**五、标签部分落库。** 认得出的标签直接写进账本，三张表都不认的词记进 `note.pending_genres`。
这一行照旧摆在复核页上，要判的只剩那几个词；词一收录（静态表或 `genre_decision`），这一行
自己消失。

**六、出演者的企划名义先用本机证据换主艺名。** 按番号读本机已落盘的 Seesaa 素人系総合 Wiki
与 AV女優名鑑 快照，再查账本 `entity_alias`。解出唯一一个主艺名就落它，规则名记
`adr-0038-planning-alias-resolved-<证据来源>`，并把企划名义登记成该实体的别名（`entity_alias`
的 `source` 写 `javinizer:planning-alias`），这样用户搜封面上印的那个称呼仍然搜得到。不新增
站点、不发请求；解不出照旧交人工。

**七、留给人工的只有三类**：候选自报番号与文件番号对不上且整行只有这类候选（ADR-0035 决策
一）、企划名义三条路都解不出、词表还不认的那几个词。用户手改过的字段（`user:` / `review:`
署名）任何情况下不碰，ADR-0034 的这道保护不受影响。

## 理由

- 那 62 行官方分歧不是「无法判断」，是「早就判断过了」：链上把片商排在转售店前面，正是
  用户在页面上逐条点的时候做的那个判断。让他把同一个判断重做 62 遍没有产出。
- 分层要落在来源的性质上，不是站点名单上。`local_nfo` 是人已经写过的结论，官方是发行方
  自己写的事实，javdb 是社区里交叉校验过的那一家，javbus 是搜不到就近似命中的那一家——这
  四句话就是链。
- 企划名义那 69 行里，缺的从来不是判断力，是把两份本机已有的文件对起来看一眼。
- 标签那 78 行暴露的是判断粒度错了：候选行是落库的单位，不该同时当复核的单位。

## 被否决的方案

- **给 `/scraping` 加一个配置字段优先级与黑名单的界面。** 本机当前一条例外都不需要，先建
  界面就是先建一个没有内容的入口。两张表留在策略层，真出现第一条例外时再谈界面。
- **让链也管覆盖，社区来源胜出就能改掉账本已有的值。** 只读普查显示本机 55 条替换全是官方
  （dmm 28、libredmm 26、r18dev 1），社区来源一条都没有。放开它换不来任何一行，却把
  ADR-0033 的边界一起拆了。
- **企划名义按宣传语里的关键词猜人名。** ADR-0025 否决过，这里不重开。
- **同一家给出两个值时按出现顺序取第一个。** 那是拿 CSV 的行序冒充判断。

## 后果

- 本机队列从 438 行降到 184 行：143 行自动结算（tags 78、title 28、series 28、performers 5、
  studio 4），111 行作为兜底挑战被剔除。自动结算里 78 行留着待判的词，卡片仍在页面上。
  143 行按规则名分：`adr-0018-empty-field-single-official-source` 69、`adr-0038-chain-libredmm`
  32、`adr-0038-chain-dmm` 28、`adr-0018-empty-field-single-community-source` 7、
  `adr-0038-planning-alias-resolved-sougouwiki` 3、`adr-0025-empty-field-2-agreed-official-sources`
  2、`adr-0038-planning-alias-resolved-entity-alias` 2。链取舍的 60 行被压下的全是 mgstage。
- 留给人工的 184 行：企划名义解不出 69、文件名认不出番号 46、MIB 番号非官网 42、候选番号
  对不上 19、账本已无该资产 8。
- ADR-0034 的规则名 `adr-0034-empty-field-javdb-preferred` 不再产生，同一类行改记
  `adr-0038-chain-javdb`；回溯历史决定时两个前缀都要捞。
- ADR-0035 决策三的「只剩官方来源可替换现值」扩到包含 `local_nfo`。
- `metadata_auto_apply_candidate` 的对外签名不变，复核页「通过」按钮与后台任务仍走同一份
  实现，链与人工队列不会各判各的。
