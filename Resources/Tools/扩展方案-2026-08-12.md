## 二、三条不可违反的约束

写在最前面，后面所有设计都受它约束。

### 2.1 网盘上不能跑本地那套内容级流水线

CloudDrive2 把 115 挂成 `Z:\`，**看起来**像本地盘，但每次读取文件内容都是真实下载。

- 抽帧一个视频 = 下载几 MB 到几十 MB
- 解压 = 完整下载
- PHash = 完整解码

对 13.6 TB 的库全量做一遍，产生的流量和请求数足以触发 115 的限速与风控。

**因此：网盘侧的整理只用「零下载成本」的信息 —— 文件名、路径、大小、以及网盘自己提供的哈希。**
需要看内容才能判断的（伪装、真实创作者、行为标签），一律推迟到文件**落地本地之后**再做。

### 2.2 哈希是网盘去重的唯一正解

三家网盘的秒传机制都基于内容哈希，这意味着哈希是**服务端已经算好的、白拿的**：

| 网盘 | 哈希 | 备注 |
|---|---|---|
| 115 | SHA1 | 开放平台 API 直接返回 |
| PikPak | gcid | API 返回；userscript 的「hash 精确匹配」用的就是它 |
| 百度 | MD5（分片 MD5 + 整文件 MD5） | 官方个人 API 受限，见 §四.3 |

**精确重复用哈希，零成本、零误判。** 不要用文件名做精确去重 —— 同一个文件在不同分享里名字几乎必然不同。

### 2.3 PLM 与 Stash 不可同时管库

已在 README 记录。扩展到网盘侧同样成立：**不要让 CloudDrive2 的任何自动整理功能和本方案同时改同一批路径**。

## 三、核心架构变更：引入全局账本

### 3.1 为什么现在的 manifest 不够

`Intake\manifest\<批次ID>.json` 是**每批次一个文件**。它能回答「这批是什么时候从哪下的」，但回答不了：

- 这个链接我是不是已经下过了？
- 这个文件和库里某个文件是不是同一个？
- 这个创作者我总共存了多少、最近一次是什么时候？
- 我搜过但没找到的东西有哪些？

而**去重、推荐、迭代这三件事全都需要跨批次的全局查询**。

### 3.2 方案

新增 `R:\Resources\Intake\ledger.db`（SQLite，单文件，纯本地）。
**per-batch JSON 保留不动**，继续作为审计留档；ledger 是它的索引层。

```sql
-- 来源：一条链接/一个分享/一次离线下载
CREATE TABLE source (
  id INTEGER PRIMARY KEY,
  batch_id TEXT,              -- 对应现有 manifest 的批次ID
  url TEXT,                   -- 原始链接
  url_norm TEXT UNIQUE,       -- 归一化后的链接，用于判重
  title TEXT,                 -- 页面标题
  password TEXT,              -- 解压密码
  platform TEXT,              -- 115 / pikpak / baidu / http / magnet
  note TEXT,
  registered_at TEXT,
  status TEXT                 -- 已登记 / 已下载 / 已处理 / 已入库 / 失败 / 放弃
);

-- 资产：一个具体文件，不论它在本地还是网盘
CREATE TABLE asset (
  id INTEGER PRIMARY KEY,
  source_id INTEGER REFERENCES source(id),
  location TEXT,              -- local / 115 / pikpak / baidu
  path TEXT,                  -- 该 location 下的完整路径
  filename TEXT,
  size INTEGER,
  hash_kind TEXT,             -- sha1 / gcid / md5 / none
  hash TEXT,
  duration REAL,              -- 仅本地或 API 提供时填
  phash TEXT,                 -- 仅本地填，来自 Stash
  creator TEXT,               -- 归属创作者
  stash_scene_id INTEGER,
  snapshot_path TEXT,
  first_seen TEXT,
  last_seen TEXT
);
CREATE INDEX ix_asset_hash ON asset(hash_kind, hash);
CREATE INDEX ix_asset_size ON asset(size);

-- 检索意图：搜过什么、找到没有。推荐系统的反馈来源
CREATE TABLE quest (
  id INTEGER PRIMARY KEY,
  keyword TEXT,               -- 搜索词 / 创作者名 / 标签
  origin TEXT,                -- browsing_history / gap_analysis / manual
  created_at TEXT,
  resolved_at TEXT,
  outcome TEXT                -- found / not_found / dropped
);
```

### 3.3 落地方式

- `rm-register.ps1` 增加写 ledger 的 `source` 行，并在写之前先查 `url_norm` —— **登记时就告诉你「这个下过了」**
- `rm-process.ps1` 处理完每个文件时写 `asset` 行
- `rm-import.ps1` 回填 `stash_scene_id` 和 `phash`
- 新增 `rm-ledger.ps1`：查询/统计/导出

优先级最高，因为后面 §五 §七 全都依赖它。

## 四、网盘接入

### 4.1 统一走 CloudDrive2，不给每家写对接

CloudDrive2 已装（`C:\Program Files\CloudDrive2`）且已挂 115 到 `Z:\`。它同样支持 **PikPak** 和 **百度网盘**。

**建议：在 CloudDrive2 里把 PikPak 和百度也挂上，得到统一的文件系统视图。**

```
Z:\115open\...      已挂
P:\...              PikPak    ← 待挂
B:\...              百度       ← 待挂
```

好处是所有「列目录、读文件名、读大小」的操作在三家之间写法完全一致，本地脚本不用改。
代价是**读内容仍然是下载**，所以 §2.1 的约束照样适用。

### 4.2 哈希从哪来

CloudDrive2 的文件系统视图**不暴露哈希**。所以哈希要单独取：

- **115**：走开放平台 API（挂载点叫 `115open` 说明 token 已经有了）。列目录接口直接返回每个文件的 `sha1`
- **PikPak**：官方 API 返回 `hash`（gcid）。也可以直接用 **PikPak_Enhancement_Master** 这个 userscript 的「目录树导出」功能，它导出的结构里带哈希，一次性拿全库
- **百度**：见下

新增 `rm-cloudscan.ps1`：调各家 API 拉全量文件清单（路径 + 大小 + 哈希），灌进 `asset` 表，`location` 分别标记。
**这一步不下载任何文件内容**，只是元数据，13.6 TB 的库拉一遍也就几十 MB 的 JSON。

### 4.3 百度网盘是三家里最难的，降级处理

百度没有可用的个人开发者 API（开放平台面向企业，个人申请基本批不下来），社区方案都依赖抓客户端 token，稳定性差且有封号风险。

**建议不要投入自动化，按这个降级顺序**：

1. CloudDrive2 挂载 → 至少拿到路径/文件名/大小，能做「同名同大小」级别的粗去重
2. 需要精确去重时，手动导出百度客户端的文件列表（客户端支持导出）
3. **战略上：把百度当冷备，不当活跃库。** 新资源优先落 115 和 PikPak

理由：你的 115 已经是 13.6 TB 的主力，百度多半是历史遗留。把整理精力投在 115 上回报最高。

### 4.4 PikPak userscript 的定位

`digbug82/PikPak_Enhancement_Master` 是**浏览器 userscript**（Tampermonkey 类），直接调 PikPak 的 API。它和本地流水线是**互补，不是替代**：

| 它擅长（云端侧，落地前） | 本地流水线擅长（落地后） |
|---|---|
| 分享链递归解析、存前预览 | 递归解压、去伪装 |
| 哈希/时长/名称相似度去重 | PHash 视觉去重 |
| 批量改名（正则/剧集编号） | 创作者归集 + Stash 打标 |
| 目录树导出、M3U 生成 | 关键帧快照留档 |
| 密码本 | 密码本 |
| 16 帧截图 | 9 帧接触表 |

**两个接点必须打通**：

1. **密码本双向同步** —— 它有 password vault，你有 `passwords.txt`。它支持配置导出，写个小转换脚本互导，否则两边各记一半，最难受
2. **目录树导出 → ledger** —— 它导出的目录树是 §4.2 拿 PikPak 全库元数据最省事的方式，直接解析进 `asset` 表

注意它是 AGPL-3.0，自用无所谓，别把改动过的版本再分发出去就行。

## 五、网盘存量整理

对着 13.6 TB 做，顺序很重要 —— **先做零成本的，把量降下来，再做有成本的**。

### 第 1 层：精确重复（零下载）

`asset` 表里 `hash` 相同的行分组。同一哈希多份 = 确定重复，保留路径最规范的一份，其余进待删清单。

这一层通常能消掉网盘库里最大的一块 —— 反复转存同一个分享是最常见的重复来源。

### 第 2 层：疑似重复（零下载）

哈希不同但高度可疑的组合：

- **大小完全相同** 且 文件名相似度 > 0.8 → 极可能是同内容不同封装
- **同一目录下连号文件**（`xxx (1).mp4`、`xxx (2).mp4`）
- **文件名归一化后相同**（去掉站点前缀、分辨率后缀、`@频道` 标记后比较）

这一层**只产出候选清单，不自动删**。

### 第 3 层：视觉重复（有下载成本，抽样做）

只对第 2 层的候选组做，且**每个视频只抽 3 帧**（首/中/尾各一），算感知哈希比对。
一个候选组的成本约几 MB，而不是整个文件。

Stash 本身有 PHash 能力（README §六 记的「按需生成精灵图/PHash」还没做）。
**本地库应该先把 PHash 建起来** —— 这不但解决本地去重，还给网盘侧提供了比对基准：
网盘上抽帧算出的 PHash 可以直接和本地库比，判断「这个网盘文件我本地是不是已经有了」。

### 第 4 层：分类

网盘侧**不做**本地那种创作者物理归集（移动网盘文件成本高、易出错、且 115 的移动操作有频率限制）。

改为**虚拟分类**：分类结果只写进 ledger 的 `creator` 字段，不动网盘上的实际路径。
需要看的时候用 ledger 查询生成清单。真要物理整理，等它落地到本地时由现有流水线处理。

判定依据按可靠性：文件名文本 → 目录名 → 与本地已知创作者的名称/别名匹配（复用 `rm-tagmap.ps1` 的 `$Performers` 词典）。

### 删除策略

**任何一层都不自动删除。** 产出 CSV 待删清单 → 人工过目 → 执行时先移到网盘的回收目录而非直接删。
理由和本地流水线一致：`quarantine` 而非静默丢弃。

## 六、落地自动化

现在是手敲 `rm-process.ps1 -Batch xxx`。补两件事：

### 6.1 目录监视

`rm-watch.ps1`：用 `FileSystemWatcher` 盯 `R:\Inbox\`，某个批次目录**连续 N 分钟没有新写入**（说明下载结束）就自动触发 `rm-process.ps1`。

用「静默期」而不是「文件出现」来判断，因为下载中的文件会持续增长。建议 N = 3 分钟。

### 6.2 下载器对接

| 下载方式 | 对接办法 |
|---|---|
| PikPak 客户端 | 设置里把下载目录指到 `R:\Inbox\_pikpak\`，watcher 覆盖 |
| 115 浏览器 | 同上，指到 `R:\Inbox\_115\` |
| 浏览器直下 | 同上 |
| CloudDrive2 挂载盘直接复制 | 复制目标选 `R:\Inbox\<批次>\` |

**登记怎么办**：自动触发的批次没有 `rm-register` 提供的链接和密码。
方案是 watcher 建一个「待补登记」的 source 行，处理照常跑，但在结果里标记「来源未知」，
等你有空时用 `rm-ledger.ps1 -Orphans` 列出来批量补。**宁可先处理、后补登记，也不要因为没登记就卡住。**

### 6.3 剪贴板辅助（可选，但很省事）

一个后台小脚本：检测到剪贴板内容是分享链接格式（115/PikPak/磁力/常见站点），
弹一个轻量提示问「要登记吗」，一路回车就完成 `rm-register`。
**这是把「记录链接和密码」这件事从「需要自律」变成「顺手」的关键。** 你原本最容易漏的就是这一步。

## 七、浏览记录 → 推荐与迭代

这是全新的部分，也是最有价值的部分。核心思路一句话：

> **把「你想看什么」（浏览记录）和「你实际有什么」（Stash 库存）做差集，差出来的就是该去找的。**

### 7.1 数据源汇总

| 源 | 规模 | 状态 |
|---|---|---|
| Zen `places.sqlite` | 77,680 URL | ✅ Mac 侧已分析 |
| Safari（iOS 同步） | 16,161 URL | ✅ Mac 侧已分析 |
| Windows Chrome 残余 | 370 域名 / 3,229 URL | ✅ 本次抢救，见 `chrome-win-gap.txt` |
| **Google Takeout My Activity** | ? | ⏳ 已导出，待传到 Windows |
| Stash 库存标签分布 | 2,551 场景 | ⏳ 待统计 |

### 7.2 构建「口味向量」

把浏览记录里的信号归一化成带权重的维度表。Mac 侧已确立九个维度（Oral / Feet / Anal / Position /
Cumshot / Dynamic / Body-Species / Meta / ASMR），本次 Windows 残余又补出两条线索：

- `hsex.men` 搜 `尿` —— 排尿/失禁，**九个维度里没有**
- `mazii.net` 查 `鈴口` —— 独立源交叉印证了 Oral 维度的精细度

Takeout 导入后重跑一次，权重才算稳。

### 7.3 构建「库存向量」

从 Stash GraphQL 拉每个标签的场景数。这是「你实际有什么」。

### 7.4 差集 = 待补清单

```
缺口分 = 口味权重 × log(1 + 口味权重 / (1 + 库存数))
```

分数高的就是「你反复搜但库里几乎没有」的东西。产出两类可执行输出：

1. **待找关键词清单** → 写进 `quest` 表 → 拿去 115/PikPak 搜索、去订阅站找
2. **待补创作者清单** → 浏览记录里出现过、但 `R:\Media\创作者` 里没有的
   本次已经差出几个：`ichiichini`(Fanbox)、`hisfavpassenger`(OnlyFans)、`yuki_ch55`、
   `fantia.jp/fanclub/1419`、`ci-en creator/30722`、`愛世くらら`

### 7.5 迭代闭环

每次入库后重算库存向量 → 缺口分自动下降 → 清单自动更新。
`quest` 表记录搜过没找到的，避免反复搜同一个死胡同。

建议**每月跑一次**，产出一份「本月该找什么」的报告。这就是你要的「AI 全面介入迭代」——
不是让 AI 替你下载，而是让它持续告诉你**该找什么、哪里还缺**。

### 7.6 一个诚实的提醒

浏览记录反映的是**检索行为**，不完全等于**偏好** —— 反复搜某个东西也可能是因为一直没找到好的。
所以缺口分只作为**建议**，最终清单需要你过一眼。真正的偏好信号是 Stash 里的评分和观看次数，
但那需要你开始用评分功能，数据才会积累起来。

## 九、边界（沿用现有约定）

- 只动 `R:`、`%LOCALAPPDATA%\Stash`、`Intake` 下的产物；不碰 Disk 0 / LaCie / Xiaomi
- 不上传任何文件名、封面、指纹、媒体或浏览记录到第三方
- 联网仅限：按**作品名**查公开资料、调用三家网盘自己的 API
- 任何批量操作先出映射预览再执行，执行后核对文件数与总字节
- 网盘删除一律先移回收目录，不直接删
- Stash 仅绑 `127.0.0.1:9999`
- ledger.db 与 manifest JSON 都留在本地，不进任何同步盘
