## 零、先说清楚要解决的真问题

现状盘点：

| 层 | 规模 | 你能「看见」多少 |
|---|---|---|
| 本地 `R:\Media` | 843 GB / 2,552 文件 | Stash 里 2,551 场景，105 个标签 |
| 115 | 13.34 TB / 35,737 文件 | **几乎为零** —— 顶层是转存批次，无标签 |
| PikPak | 9.88 TB / 62,416 文件 | **零** |
| Pixiv | 996 位关注 | 只在网页上 |
| X | 176 个成人向关注 | 只在时间线上 |

**23.2 TB、30,000 个视频，其中 97% 你实质上是看不见的。**
搜索解决不了这个 —— 搜索要求你先知道要搜什么。而「找配菜」的本质是**你不知道**。

所以涌现模式不是锦上添花的功能，它是让这 23 TB 从「仓库」变成「可消费的库」的唯一途径。

## 一、四个必须先承认的约束

### 1.1 你没有消费数据，这是最大的短板

现在能拿到的全部信号 —— 浏览记录、搜索词、关注列表 —— **反映的都是「找」，不是「爱」**。

反复搜「二十万人电报群…毒龙」80 次，可能说明它极合口味，也可能说明**一直没找到，所以一直在搜**。
这两种情况在数据上完全无法区分，但推荐含义相反。

Stash 有评分、O-counter、播放次数、播放进度，**目前全是空的**。

> **结论：涌现模式的第一优先级不是写推荐算法，是开始采集消费信号。**
> 没有它，推荐只能靠"你搜过什么"猜，而那个信号是有偏的。

### 1.2 内容标签必须靠关键帧，不能靠文件名

网盘上 30,000 个视频，文件名形态是 `www.98T.la@569.avi`、`0921874e-dd00-442f.m4v`、
`auto_create@2022.9.12 09.06.39 (409)\...`。靠文件名做标签的命中率已经实测过 —— 大量误判
（`ts` 命中 GETS、`3d` 命中 UUID、`69` 命中 569.avi）。

好消息是**抽帧成本已实测可行**：seek 抽帧 0.37–1.36 秒/帧，**与文件大小无关**
（8.5 GB 的文件和 0.36 GB 的一样快），因为只读 moov atom + 目标 GOP。
全库 30,000 视频 × 9 帧 ≈ 6 路并行一夜跑完。

### 1.3 在线资源不该下载了才索引

Pixiv 996 位关注、X 176 个艺术家，这两条线**基本没转化成文件**，那是在线消费模式。
硬要"补全下载"会产生一堆你只想在线刷的东西。

> **索引指针，不索引文件。** 推荐时给链接，想留再下。

### 1.4 涌现感来自受控随机，不来自复杂模型

不需要 embedding、不需要 GPU、不需要训练。
涌现 = **标签共现 + 加权采样 + 一条刻意的"意外通道"**。
过度工程化会让这个项目永远停在"在建"状态。

## 二、三层描述模型

现在的标签体系只有一层（内容标签）。涌现需要三层。

### 事实层 —— 白拿，ffprobe 直接读

分辨率、时长、编码、码率、帧率、宽高比、音轨有无、文件大小。
**零判断成本，准确率 100%。** 已在本地流水线做了，网盘侧照搬。

### 感知层 —— 内容标签，靠关键帧 + 文件名 + 已有词典

沿用 `rm-tagmap.ps1`，但按五源汇总的结论重排优先级（见 §三）。

### 情境层 —— 这一层现在完全没有，而它才是涌现的关键

「配菜」和「正片」的区别不在题材，在**情境**：

| 情境维度 | 取值 | 怎么得到 |
|---|---|---|
| **时长档** | 速食(<5min) / 短(5–15) / 中(15–40) / 长(>40) | ffprobe，白拿 |
| **屏向** | 竖屏(手机) / 横屏(电脑) | ffprobe，白拿 |
| **画质档** | 4K / 1080P / 渣画质 | ffprobe，白拿 |
| **节奏** | 直接进入 / 慢热有前戏 | 关键帧：前 20% 的帧是否已是正片内容 |
| **剧情感** | 纯肉 / 有剧情 | 关键帧：场景切换频率 + 是否有对白字幕 |
| **声音** | 有原声 / 无声 / 音声向 | ffprobe 音轨 + 响度分析 |
| **单人/多人** | 独角 / 双人 / 多人 | 关键帧：人脸/人体计数 |
| **熟悉度** | 常看创作者 / 从没碰过 | 消费数据（§一.1） |

**「配菜」的典型情境组合 = 速食 + 竖屏 + 直接进入 + 熟悉。**
这个组合在现有标签体系里一个都表达不了 —— 这就是为什么现在没法"找配菜"。

## 二又四分之三、全生命周期介入

这个项目要管的不是「一个库」，而是**资源从被发现到被消费的整条链路**，四个环节首尾相接成闭环：

```
        ┌─────────────────────────────────────────────────┐
        │                                                 │
   ①搜集 ──▶ ②下载 ──▶ ③管理 ──▶ ④消费 ──▶ 反馈信号 ──┘
        ▲                                    │
        └────── 缺口分析 ◀── 口味模型 ◀──────┘
```

**关键在于它是闭环**：消费产生反馈 → 反馈修正口味模型 → 口味模型减去库存得出缺口 →
缺口驱动搜集。没有这个回路，前三个环节只是一条越堆越大的传送带。

### ① 搜集 —— 四条进料线

| 线 | 对象 | 手段 | 频率 | 现状 |
|---|---|---|---|---|
| **追更** | X 关注 30+ 3D 艺术家 | Kemono/Coomer 镜像轮询（他们的 Fanbox/Patreon 多被镜像） | 每日 | ⏸ |
| | Pixiv 996 位关注 | PixivBatchDownloader 按关注拉新作 | 每周 | ⏸ |
| | DLsite 210 作品 / Ci-en 57 创作者 | 新作与更新推送页 | 每周 | ⏸ |
| | F95zone 已下载的 10 款 | **版本号比对**（DesertStalker 0.19.2→0.21.3 就是这么发现的） | 每周 | ⏸ |
| **论坛监控** | 南+ 免空资源区/茶馆、司机社国产视频 | 新帖标题按口味维度关键词匹配 | 每日 | ⏸ |
| **缺口驱动** | 口味模型 − 三处库存（本地/115/PikPak）的差集 | 生成待找关键词与待补创作者清单 → `quest` 表 | 每月 | 🔄 部分 |
| **顺手捕获** | 剪贴板里的分享链 | 检测到 115/PikPak/磁力/论坛链接就弹窗问「要登记吗」 | 实时 | ⏸ |

> 最后一条看着琐碎，但它解决的是**唯一一个依赖自律的环节**。你原本最容易漏的就是「记下链接和密码」。

### ② 下载 —— 优先级与登记

**优先级**（决定资源落在哪）：

1. **网盘离线转存优先** —— 115/PikPak 的离线下载。不占本地带宽和空间，且 23 TB 主体已在网盘
2. **直链/磁力 → 本地 `R:\Inbox\<批次>`** —— 需要立刻处理（解压/去伪装）的走这条
3. **论坛附件** —— 需要登录态，半自动

**铁律：登记先于下载。** `rm-register.ps1` 已建成 —— 把链接、解压密码、来源帖、时间当场钉住。
事后补登记的成本远高于当场记。自动落地的批次由 watcher 建「待补登记」记录，
**宁可先处理、后补登记，也不要因为没登记就卡住**。

### ③ 管理 —— 已建成的主体

```
落地 → 递归解压（密码本自动试） → 去伪装（magic bytes + ffprobe 兜底）
     → 关键帧接触表 → 创作者归集 → 改名清理 → 入 Stash + 账本
```

账本（`ledger.db`）统一索引**本地 + 115 + PikPak + 在线**四处，
`location` 字段区分。「我有没有这个东西」查一次就能同时回答四边。

Stash 三轴分工（2026-08-13 建立）：**Studio = 频道/社团，Performer = 出镜者，Tag = 内容**。

### ④ 更新 —— 四类维护

| 类型 | 做什么 | 触发 |
|---|---|---|
| **追更落地** | 把 ① 抓到的新内容走完 ②③ | 每日/每周 |
| **库健康** | ffprobe 失败的坏文件清单；失效的网盘链接；新增重复（SHA1 增量比对） | 每月 |
| **口味模型重算** | 新数据源接入时重跑五源汇总 | 按需（本次 Firefox 接入就是一例） |
| **消费信号回流** | 播放记录、评分、显式反馈写回账本 | 实时 |

### 各环节现状一览

| 环节 | 已建成 | 缺口 |
|---|---|---|
| ① 搜集 | 缺口分析（部分） | **四条追更线全部未上线**；剪贴板辅助未做 |
| ② 下载 | `rm-register` 登记 | 网盘离线转存未接入；watcher 自动触发未做 |

## 四、统一索引：ledger 扩展

在 `扩展方案` §三 的基础上扩三个字段维度。

```sql
CREATE TABLE asset (
  id INTEGER PRIMARY KEY,
  -- 定位
  location TEXT,       -- local / 115 / pikpak / online
  path TEXT,           -- 本地/网盘=路径；online=URL
  medium TEXT,         -- video / image_set / game / audio / illustration
  -- 身份
  hash_kind TEXT, hash TEXT,      -- sha1(115) / gcid(pikpak) / phash(本地)
  creator TEXT, series TEXT, code TEXT,   -- 创作者 / 系列 / 番号
  -- 事实层（ffprobe）
  duration REAL, width INT, height INT, vcodec TEXT,
  bitrate INT, fps REAL, has_audio INT, filesize INT,
  -- 情境层
  ctx_length TEXT,     -- 速食/短/中/长
  ctx_orient TEXT,     -- 竖屏/横屏
  ctx_quality TEXT,    -- 4K/1080P/渣
  ctx_pace TEXT,       -- 直接/慢热
  ctx_people TEXT,     -- 独角/双人/多人
  -- 消费信号（核心，见 §五）
  play_count INT DEFAULT 0, last_played TEXT,
  rating INT, o_count INT, watch_ratio REAL,
  -- 溯源
  source_id INTEGER, snapshot_path TEXT, first_seen TEXT
);
CREATE TABLE asset_tag (asset_id INT, tag TEXT, confidence REAL, source TEXT);
CREATE INDEX ix_tag ON asset_tag(tag);
```

`asset_tag.source` 记标签怎么来的（`filename` / `keyframe` / `manual` / `stash`），
`confidence` 让推荐时能优先用可信标签、也能事后审计误判。

## 五、消费信号采集 —— 优先级最高

没有这个，后面全是空中楼阁。三个来源，成本从低到高：

### 5.1 Stash 自带（零成本，立刻能开）—— 2026-08-13 核实

**不用自己造。** 查过 Stash 0.31.1 的 GraphQL schema，你要的观看统计字段一个不缺：

| 你要的 | Stash 现成字段 | 怎么算 |
|---|---|---|
| 观看时长 | `play_duration`（累计秒） | 直接读 |
| 切走点 | `resume_time`（上次退出位置） | 直接读 |
| **切走率** | 无现成字段 | `1 - play_duration / (play_count × file.duration)` |
| 观看次数 | `play_count` | 直接读 |
| 每次观看的时间点 | `play_history`（时间戳数组） | 直接读，能看出昼夜/周期规律 |
| 高潮信号 | `o_counter` / `o_history` | 比评分诚实得多的偏好指标 |
| 显式评分 | `rating100` | 手动 |
| 自定义标记 | `custom_fields`（任意 KV） | 存"不满意/待删/已处理"用这个 |

写入的 mutation 也是现成的：

```
sceneSaveActivity(id, resume_time, playDuration)   # 播放器每隔几秒调一次
sceneAddPlay(id, times)   sceneAddO(id, times)
sceneDeletePlay(id)       sceneResetActivity(id)
```

Stash 自带的 web 播放器**已经在调 `sceneSaveActivity`**。也就是说：只要播放走 Stash（或走我们的 Web 层再回调这个 mutation），埋点是白得的。

**当前实测：2,551 个 scene 里只有 5 个有播放记录，0 个有 O 计数，0 个有评分。**

这个数字说明一件事，而且是整个方案里最关键的一条：

> **反馈闭环现在是空的，而且只要消费还发生在 PotPlayer / 直接双击文件，它就会永远是空的。**
> 所以那个局域网 Web 界面不是锦上添花，它是拿到消费数据的**唯一**通道。
> 路线图里它排在第四期是错的 —— 应该提到第二期并行做，先做「能播 + 能埋点 + 能反馈」这个最小壳，
> 标签体系可以边用边补，但数据一天不采就永远缺一天。

### 5.2 播放器历史（低成本）

PotPlayer 有播放历史（注册表/配置文件），能拿到"看过什么、看了多久"。
定期导入 ledger。这条覆盖你在挂载盘上直接看的那部分 —— 也就是 23 TB 的主要消费方式。

### 5.3 显式反馈（推荐时顺手给）

涌现模式每次出候选，都带一个极简反馈：`👍 / 👎 / 已看过`。
一次点击的成本，换的是最干净的信号。**这是冷启动阶段最有价值的数据。**

> 建议：前两个月主要靠 5.3 攒数据，5.1/5.2 作为被动补充。
> 攒够约 200 条显式反馈，推荐质量会有质变。

### 5.4 反馈动作分级 —— 2026-08-13 新增

网盘里有大量随手加的资源，看到不满意的必须能当场处理。但**处理不等于删除**，
分四级，因为它们喂给模型的信号完全不同：

| 动作 | 落地 | 信号含义 | 可逆 |
|---|---|---|---|
| 👎 **不合口味** | `custom_fields.taste = dislike` | 内容维度不对 —— 拉低同 tag 组合的权重 | 是 |
| 😐 **看过了/腻了** | `custom_fields.taste = seen` | 内容对，但已消费 —— 只降**近期**权重，不降维度权重 | 是 |
| 🗑 **标记待删** | `custom_fields.disposal = pending` + 打 Tag `待删` | 质量差/画质烂/重复 —— **不删文件**，进清单 | 是 |
| ❌ **执行删除** | 走 `cloud-delete.py`，CSV → 核对 → 执行 → 留日志 | 攒够一批统一执行 | 否 |

**关键设计：前三级都是打标记，一次点击零风险；只有第四级动文件，且必须批量走既定的
「先出 CSV 再执行」流程。** 涌现界面里只出现前三个按钮，第四级永远在别处、永远要二次确认。

区分 👎 和 😐 很重要 —— 它们混在一起会毒化模型：
「这个女优我很喜欢但这部看过三遍了」如果被记成 dislike，会把整条口味线打歪。

**切走率的解读同理。** `1 - play_duration/(play_count × duration)`：

- 切走率高 + 切走点在**开头** → 封面骗人 / 一眼不对 → 强 dislike 信号
- 切走率高 + 切走点在**中后段** → 内容对，只是够了 → 这是**正**信号，不是负的
- 切走率低（看完） + `o_counter` 有增 → 最强正信号

所以光记「切走率」不够，**必须同时记切走点在片长的哪个位置**（`resume_time / duration`）。
这个比值是整套反馈里信息量最大的单个数字。

## 六、涌现模式的实现

### 6.1 心情词典 —— 从自然语言到查询

不做 NLP，做**一张可手改的映射表**。冷启动靠手写，之后按反馈迭代。

```yaml
快 / 来点快的 / 没时间:
  ctx_length: [速食, 短]
  ctx_pace: 直接
  sort: 熟悉度降序          # 想快就别冒险

慢慢来 / 有时间 / 沉浸:
  ctx_length: [中, 长]
  ctx_pace: 慢热
  tags_boost: [剧情, ASMR, 音声]

手机 / 躺着:
  ctx_orient: 竖屏
  ctx_length: [速食, 短]

想看新的 / 腻了:
  filter: play_count = 0
  sort: 匹配度 × 随机
  novelty: 0.4              # 提高意外通道比例

熟悉的 / 稳的:
  filter: rating >= 4 OR play_count >= 2
  novelty: 0.05

足 / 脚 / 丝袜:
  tags: [足交, 丝袜, 裸足, 足指]     # 主轴，单独成词
  cross_medium: true                  # 同时给本地+网盘+Pixiv+X
```

用户输入直接匹配词典键（支持模糊），命中多条就取交集。
**关键词和心情走同一套机制** —— 关键词就是直接指定 tags。

### 6.2 候选生成：三条通道混合

```
候选池 = 精准通道(60%) + 邻接通道(30%) + 意外通道(10%)
```

- **精准通道**：严格匹配心情词典解出的条件，按 `匹配度 × 熟悉度` 排序
- **邻接通道**：在标签共现图上走一步。你爱「足交+丝袜」→ 推「足交+瑜伽裤」
  （共现图从 ledger 的 asset_tag 直接统计，不需要模型）
- **意外通道**：从口味向量覆盖到、但**库存里你从没碰过**的区域随机采样。
  这是"涌现"真正发生的地方 —— 23 TB 里绝大部分你从没看过

每次出 **5–8 个**，多了等于没推荐。每个候选给：一张关键帧接触表 + 时长/画质/创作者 + 一键打开
+ §5.4 那三个反馈按钮。

### 6.2b 第四通道：联网通道 —— 2026-08-13 新增

上面三条都在 23 TB 库存里打转。但**库存是幸存者偏差**（这是整个项目最早确立的一条），
真正的口味覆盖面一定比库存大。所以要有第四条：

```
候选池 = 精准(50%) + 邻接(25%) + 意外(10%) + 联网(15%)
```

**联网通道做什么：** 把口味模型解出的条件翻译成**站外查询**，去公开来源找库里没有的东西，
出的是「可获取的候选」而不是「可播放的文件」——
命中后进 §二又四分之三 的搜集/下载环节，形成闭环。

三种查法，成本递增：

| 查法 | 怎么做 | 成本 |
|---|---|---|
| **追更命中** | 已订阅的创作者出新 → 直接进候选池 | 零（RSSHub 已在拉） |
| **同类扩展** | 拿高分作品的番号 → 查同女优/同厂牌/同 series 的其他作品 → 查库里有没有 → 没有则进候选 | 低（r18.dev 一次 API） |
| **标签检索** | 把心情词典的 tag 翻成站点的检索词，去公开索引站搜 | 中（要维护每站的检索语法） |

前两种现在就能做，第三种等前两种跑顺了再说。

**"有时也可以推荐点不一样的"** —— 联网通道天然适合承担这个：
在口味向量的**边缘**（相似度 0.4–0.6 的带状区域）采样，而不是在中心采样。
中心是"更多同样的东西"，边缘才是"可能会喜欢但没想到"。
这条带的宽窄做成可调参数，反馈数据攒够后自动校准。

⚠️ **边界不变：出网的只有番号 / 作者名 / 通用标签词，绝不带本地路径、文件名、指纹、库存清单。**
所以联网通道**不能**用"把我的库传上去找相似"这类做法（StashDB / ThePornDB 的指纹匹配即属此类，默认不启用）。

### 6.3 跨媒介混合

同一次推荐里可以混：

```
[本地]  跳跳羊 - 沉溺舞者      12min 1080P 竖屏     → Stash 打开
[115]   足交仙人 / xxx.mp4     8min  4K            → PotPlayer 打开挂载路径
[Pixiv] 作者 うるしばら 新作     插画                → 浏览器打开
[X]     @mugibunbun 本周更新    3D                  → 浏览器打开
```

**这是"全能项目"的具体含义** —— 不是四个系统并列，是一个入口后面接四个源。

### 6.4 入口：用你已有的 Telegram bot

你已经有 `冰室 Bot`（12,394 条消息，自己的 bot）。**这是最自然的入口**：

- 手机上发「想看点短的」→ bot 回 5 个候选 + 接触表缩略图 + 反馈按钮
- 本地/网盘的给可点击路径，在线的给链接
- 反馈按钮直接写回 ledger

比做网页或 CLI 都自然 —— 因为你本来就在 Telegram 里找资源。
备选入口：Stash 插件（本地内容体验最好）、CLI（`rm-suggest.ps1`，最快落地）。

## 八、路线图

> **2026-08-13 调整：Web 壳从第四期提到第二期并行。**
> 理由见 §5.1 —— 消费数据是整套推荐的燃料，而它只能从带埋点的播放器里来。
> 标签可以边用边补，数据一天不采就永远缺一天。所以先做「能播 + 能埋点 + 能反馈」
> 这个最小壳（Stash GraphQL 当后端，不自己写存储），标签和识别继续在后台跑。

**分四期，每期都有可用产物，不做大爆炸式开发。**

### 第一期：让库变得「可见」（2–3 周）

1. `ledger.db` 建表，改造 `rm-register/process/import` 写库
2. p115client 拉 115 全量清单（含 SHA1）+ PikPak 清单 → 灌 ledger
3. **全库 ffprobe**（30,000 视频，事实层 + 情境层的前三项，白拿）
4. 完成去重（710 GB 已有候选清单）

产物：**一个能查询 23 TB 的账本**。光这一步就已经比现在强得多。

### 第二期：让库有「标签」（3–4 周）

5. 全库抽帧接触表（6 路并行，一夜）
6. 关键帧识别创作者，优先 `云下载` 6.76 TB
7. 按 §三 重排标签体系：足系提为主轴、补「马眼/尿道」、扩「制服/角色扮演」和「萝莉」
8. 情境层的节奏/剧情感/人数（从关键帧推导）

产物：**每个文件都有事实层 + 感知层 + 情境层三层描述**。

### 第二期（并行）：最小 Web 壳 —— 只为采数据

不做完整界面，只做四件事，跑在局域网上、各终端浏览器可访问：

1. 列表 + 播放（后端直接用 Stash GraphQL，不自己写存储）
2. 播放埋点：定时调 `sceneSaveActivity(id, resume_time, playDuration)`
3. 三个反馈按钮：👎 不合口味 / 😐 看过了 / 🗑 标记待删（写 `custom_fields`，见 §5.4）
4. 记录 `resume_time / duration` 这个比值 —— 全套反馈里信息量最大的单个数字

产物：**消费数据开始积累**。此时第三期的推荐才有燃料。

### 第三期：涌现最小可用版（2 周）

9. 心情词典 v1（手写 20–30 条）
10. `rm-suggest.ps1` —— CLI 版三通道候选生成
11. 显式反馈写回 ledger

产物：**能用命令行找配菜**。此时开始攒消费数据。

### 第四期：入口与追更（持续）

12. Telegram bot 接入（复用冰室 Bot）
13. 四条追更线上线
14. 按反馈迭代心情词典和通道权重

## 九、几个需要你拍板的取舍

1. **消费信号怎么采？** 我建议第三期的显式反馈为主 —— 因为它最干净，且不改变你现有的看片习惯。
   如果愿意改用 Stash 播放器看本地内容，5.1 是零成本的补充。
2. **网盘要不要真的重命名归类？** 抽帧可行意味着能做，但那是几万次 API 调用。
   替代方案：只在 ledger 里做虚拟分类，网盘物理结构不动。**我倾向后者** —— 因为一旦 ledger 建好，
   物理路径长什么样就不重要了。
3. **在线源要索引到什么粒度？** 建议：Pixiv 到作者级（996 条），X 到账号级（176 条），
   不索引单个作品 —— 否则数据量爆炸且更新成本高。
4. **游戏和音声要不要进推荐？** 它们的"消费"方式和视频完全不同（几十小时 vs 十分钟）。
   建议单独一个通道，不和视频混排。

## 十、边界（不变）

- 全部本地运行，不上传任何文件名/指纹/媒体/浏览记录到第三方
- 联网仅限：按作品名查公开资料、调用各网盘自己的 API、追更源的公开页面
- 网盘上只做元数据操作和 seek 抽帧，不批量解压/整文件下载
- 删除一律先出 CSV 再人工确认，走回收目录
- Stash 仅绑 `127.0.0.1:9999`
- ledger.db 与所有分析产物留在本地，不进同步盘
