# 架构接手审计（2026-08-14）

## 结论

项目整体方向正确，可以继续做，不需要推倒重来。

真正的产品不是“23 TB 文件整理器”，而是一个只在本地/局域网运行的私人内容系统：统一索引资源，采集真实消费信号，再用受控随机和显式反馈生成推荐。先做“能播、能埋点、能反馈”的 Peach Web 壳，是正确的优先级；实际应用已在桌面和手机尺寸下工作。

当前适合把它视为一个已跑通核心闭环的原型，而不是已经稳定的长期平台。

## 正确的职责边界

### ledger.db：跨来源的唯一真相源

负责本地、115、PikPak、在线四类资产的统一身份、路径、探测结果、标签投影、消费状态和待处理任务。Peach 的列表、筛选、推荐和反馈应以 ledger 为准。

### Stash：本地视频的专业元数据与兼容层

Stash 只覆盖本地约 2,552 个文件，适合继续承担本地场景元数据、Performer/Studio/Tag 管理，以及必要的导入/导出兼容；不应再被描述成整个 Web 的后端或全局真相源。

### Peach Web：消费入口与行为采集层

通过资产 ID 串流，不向浏览器暴露文件路径；默认排除计费的 PikPak；写回播放、进度、反馈和待处理状态。它不应承担批量文件整理、删除或元数据爬取。

### 离线工具：加工与同步层

扫描、ffprobe、接触表、SHA1、识别、标签和重组继续由独立脚本完成。长任务与 Web 服务解耦是正确设计。

## 主要问题与优先级

### P0：隐私访问边界尚未真正落实

代码支持 token，但当前运行实例 token 为空，并监听 `0.0.0.0:80`。这等于同一可达网络里的设备无需口令即可浏览和串流私人库。应在确认用户设备访问方式后启用固定口令，并检查 Windows 防火墙只允许“专用网络/本地子网”。本轮先修复了 Cookie 子串误认证问题；启用口令会改变现有访问地址，未擅自切换运行实例。

### P1：行为语义分裂

CLI 使用 `rating=5/1` 表示喜欢/不喜欢，Web 使用 `feedback=dislike/seen`，另有 `play_count`、`o_count`、`watch_ratio`、`leave_ratio`、`play_seconds`、`max_reached`。这些字段能支撑原型，但推荐逻辑若直接混用会产生歧义。

下一步应先写一份行为词典，明确每个动作的唯一含义和投影规则；再增加 append-only 的行为事件表保存时间序列，`asset` 上的累计列只做快速查询投影。不要立即删旧字段。

### P1：数据库迁移没有版本

`rm-web.py` 启动时直接补列，适合一次性原型，不适合长期演进。应改为带版本号、可重复执行、启动前备份、执行后校验的迁移脚本。

### P1：缺少工程基线

仓库当前没有 Git 基线，原来没有自动化测试；Web 前后端集中在两个大文件。先补回归测试，再决定是否拆模块。不要为了“整洁”先重写框架。

### P2：首屏性能与查询模型

手机冷加载实测约 7–8 秒。首页启动同时请求多个聚合查询，90 秒内存缓存能缓解热访问，但进程重启后仍要全表聚合。应先记录接口耗时和查询计划，再针对真实慢查询加组合/部分索引，避免盲目堆索引。

### P2：文档漂移

《总体方案》一处仍写“Web 直接用 Stash GraphQL”，而实际实现已改为 ledger；《交接文档》数字也落后。保留历史判断可以，但必须增加“当前架构”入口，避免接手者按旧路线返工。

## 已接手并完成的第一批工作

- 修复 `rm-status.py` 的分母/分子口径不一致：过去把图片等非视频的 creator 也计入，导致“创作者归属 269.9%”。
- 修复 token Cookie 的子串误认证，并给登录 Cookie 增加 `HttpOnly`。
- 新增完全使用临时 SQLite 的 Web 数据层测试，不读写真实 `ledger.db`。
- 桌面与手机端完成浏览器冒烟验证；未点击播放或反馈，未污染真实消费数据。
- 首页互不依赖的 facets / tops 聚合请求改为并行；热缓存下桌面、手机首屏均约 0.5 秒出现卡片。

## 推荐的接续顺序

1. 跑稳回归测试并建立版本基线。
2. 启用局域网口令与防火墙范围限制。
3. 统一行为词典，设计 append-only 行为事件表和迁移。
4. 把 `rm-suggest.py` 改为调用统一推荐模块，Web 与 CLI 共用同一套候选生成/打分逻辑。
5. 接触表从 42.9% 继续补齐，但保持低频后台运行；不应阻塞消费闭环。
6. 再做追更 `quest` 管道，最后做完整看板。
